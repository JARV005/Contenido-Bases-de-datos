Triggers en PostgreSQL

Código que la base de datos ejecuta sola. Hoy entendemos el modelo mental: qué son, cómo funcionan por dentro y cuándo usarlos.

El problema

¿Dónde va esta regla?

"Cada vez que se modifique un producto, quiero que quede registrado quién lo hizo y qué cambió."

TechStore tiene 3 apps escribiendo en la misma BD: web, app del vendedor, panel admin.

En una app

  • Hay que repetirlo en las otras dos

En las 3 apps

  • Tres copias que se desincronizan

Alguien por psql

  • Ninguna app se entera

La regla no pertenece a ninguna app. Pertenece a los datos.

Definición

¿Qué es un trigger?

Un bloque de código que la base de datos ejecuta automáticamente cuando ocurre un evento (INSERT, UPDATE, DELETE) sobre una tabla. Nadie lo llama: se dispara solo.

🗡 Sensor de movimiento

  • No pides que la luz se encienda: te acercas y se enciende sola

✋ Reflejo

  • Quitas la mano de lo caliente sin "decidirlo"

📜 Cláusula de contrato

  • "Si pasa X, automáticamente ocurre Y"
Un procedimiento lo invocas con CALL. Un trigger no se invoca nunca: se define una vez y la BD decide cuándo ejecutarlo.
Contraste

Procedimiento vs Trigger

Procedimiento / FunciónTrigger
¿Quién lo ejecuta?Tú, explícitamenteLa BD, automáticamente
¿Se puede "olvidar"?SíNo — imposible saltárselo
¿Dónde vive la garantía?En quien lo llamaEn la tabla misma
¿Lo ve quien hace el cambio?Sí (lo escribió)No — es invisible

⚠️ Esa invisibilidad es un arma de doble filo. Volveremos a ella.

Trigger

Une función + tabla + evento + timing.

¿Por qué separados? Para reutilizar la misma función en varias tablas. Escribes fn_auditar() una vez y la enchufas a productos, clientes y ventas.
Esqueleto

Reconocer las partes

-- PARTE 1: la función (el QUÉ)
CREATE OR REPLACE FUNCTION fn_ejemplo()
RETURNS TRIGGER              ← siempre retorna TRIGGER
LANGUAGE plpgsql AS $$
BEGIN
    -- lógica...
    RETURN NEW;              ← el retorno TIENE significado
END; $$;

-- PARTE 2: el trigger (el CUÁNDO)
CREATE TRIGGER trg_ejemplo
    BEFORE INSERT OR UPDATE  timing + evento(s)
    ON productos             tabla vigilada
    FOR EACH ROW             granularidad
    EXECUTE FUNCTION fn_ejemplo();

Una sola instrucción responde: ¿cuándo? ¿ante qué? ¿en qué tabla? ¿por fila o por sentencia?

Cómo funciona

El viaje de un UPDATE

UPDATE productos SET precio = 5000 WHERE id = 3;
▼
1 · Triggers BEFORE
Puedes validar o modificar la fila. NEW aún se puede cambiar.
▼
2 · Constraints + escritura
Se verifican NOT NULL, CHECK, FK, UNIQUE y se escribe la fila.
▼
3 · Triggers AFTER
La fila ya está guardada. Ideal para auditar / notificar.
La idea que resume el día

BEFORE vs AFTER

BEFORE

La fila aún no existe.
Tu única oportunidad de cambiar lo que se guarda o rechazarlo.

CAMBIA

AFTER

La fila ya está guardada.
Modificar NEW no sirve. Reaccionas a un hecho consumado.

REACCIONA

Si hoy se llevan una sola frase: "BEFORE cambia, AFTER reacciona." Resuelve el 90% de las decisiones de diseño.
Timing

Las tres opciones de momento

Timing¿La fila ya existe?Para qué sirve¿Cambia/cancela?
BEFORENo, por escribirseValidar, normalizar, completar✅ Sí
AFTERSí, ya escritaAuditar, notificar, propagar❌ No
INSTEAD OF— (solo vistas)Hacer vistas "escribibles"Reemplaza todo

Las validaciones siempre van en BEFORE: es el único punto donde todavía puedes decir "esto no se guarda".

Granularidad

ROW vs STATEMENT

UPDATE productos SET precio = precio * 1.10;  -- afecta 100 filas

¿Cuántas veces se ejecuta el trigger?

FOR EACH ROW

  • Una vez por cada fila → 100 veces
  • Tiene acceso a NEW y OLD
  • ~90% de los casos

FOR EACH STATEMENT

  • Una vez por sentencia → 1 vez
  • NO tiene NEW ni OLD
  • Lógica sobre la operación completa

¿Mi lógica mira fila por fila? → ROW. ¿Mira la operación como un todo? → STATEMENT.

NEW existe cuando algo se crea o queda (INSERT, UPDATE).
OLD existe cuando algo existía antes (UPDATE, DELETE).

En un INSERT no hay pasado. En un DELETE no hay futuro.

Valor de retorno

El RETURN controla la operación

En una función trigger, RETURN no devuelve un dato: decide qué pasa.

En un trigger…RETURN NEW / OLDRETURN NULL
BEFORE … ROWContinúa (fila posiblemente modificada)Cancela la operación, sin error
AFTER … ROWSe ignora (la fila ya se escribió)Se ignora

RETURN NULL en BEFORE

  • Botón de "cancelar" silencioso
  • Así se hace un borrado suave: intercepto el DELETE, marco inactivo, cancelo el borrado real

En AFTER da igual

  • Se retorna NEW/OLD por convención
  • La fila ya está escrita, no hay vuelta atrás
Eficiencia

La cláusula WHEN

Condiciona el trigger para que ni siquiera ejecute la función si no se cumple algo.

CREATE TRIGGER trg_alerta_stock
    AFTER UPDATE ON productos
    FOR EACH ROW
    WHEN (OLD.stock IS DISTINCT FROM NEW.stock)  ← solo si el stock cambió
    EXECUTE FUNCTION fn_alerta_stock();

Sin WHEN

  • La función corre en CUALQUIER update, aunque solo cambie el nombre

Con WHEN

  • PostgreSQL evalúa la condición primero
  • Solo llama a la función si aplica

Usa IS DISTINCT FROM (no <>) al comparar OLD vs NEW: maneja bien los NULL.

El lado oscuro

Poder = responsabilidad

Lógica invisible

  • Alguien hace un UPDATE simple y "pasan cosas" que no escribió
  • El trigger falla y aborta una operación inocente
  • La lógica queda repartida y escondida

Cascadas

  • Un trigger modifica otra tabla… que tiene otro trigger… que modifica otra
  • Difícil de seguir, o incluso un ciclo
  • Mantén los triggers ligeros y de responsabilidad única
Regla de oro: si una constraint (CHECK, FK, UNIQUE, NOT NULL) resuelve el problema, úsala. Los triggers son para lo que las constraints no pueden expresar.
Criterio

¿Cuándo sí y cuándo no?

✅ Usa un trigger cuando…

  • La regla debe cumplirse SIEMPRE, sin importar la app
  • Auditoría / historial transparente
  • Consistencia entre tablas relacionadas
  • Validación de integridad a nivel de dato

🚫 Evítalo cuando…

  • La lógica es pesada o llama APIs externas
  • Las reglas de negocio cambian seguido
  • Una constraint simple ya lo resuelve
  • Nadie sabrá que el trigger existe (documenta)
Demo única

Todo junto: auditoría

CREATE OR REPLACE FUNCTION fn_auditar()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
    INSERT INTO auditoria (tabla, operacion, datos_anteriores, datos_nuevos)
    VALUES (
        TG_TABLE_NAME,                                   -- qué tabla
        TG_OP,                                           -- qué operación
        CASE WHEN TG_OP <> 'INSERT' THEN to_jsonb(OLD) END,  -- antes
        CASE WHEN TG_OP <> 'DELETE' THEN to_jsonb(NEW) END   -- después
    );
    RETURN COALESCE(NEW, OLD);
END; $$;

CREATE TRIGGER trg_auditar_productos
    AFTER INSERT OR UPDATE OR DELETE ON productos
    FOR EACH ROW EXECUTE FUNCTION fn_auditar();
